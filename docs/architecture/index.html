Архітектура

Шари з залежностями в один бік і дані у форматах, незалежних від рушія.

Шари

  1. Схеми (3d-*-schema): формати JSON для сцен, ассетів, мультиплеєрних сесій, збережень та інвентарів. Без рушія.
  2. Unity-пакети (3d-unity-*): системи ядра, потрібні кожній грі, набір для випуску гри та спеціалізовані для редагування, VR, сканування кімнат, Firebase, мультиплеєра, бою та інвентарю.
  3. Конструктори (3d-constructor-<style>-*, а також спільні 3d-unity-fixed-camera і 3d-unity-topdown-camera): по одному на стиль камери. Кожен додає лише свою камеру й керування (звичайні або VR) і стартовий шаблон.
  4. Пакети гри (<game>-*, наприклад game-arena-*): інтерфейс (меню, HUD) і геймплей (правила, мапи, вміст) однієї гри.

Кожен шар використовує лише шари під ним, тож виправлення в пакеті доходить до кожної гри, що на ньому побудована.

П’ять схем

  • 3d-scene-schema: де що стоїть. Читає й записує 3d-unity-scene.
  • 3d-asset-schema: що це за обʼєкти. Обробляє 3d-unity-assets.
  • 3d-network-schema: що відбувається між гравцями. Використовує 3d-unity-network.
  • 3d-save-schema: що гра пам’ятає. Конверт файлу збереження, який записує й читає 3d-unity-save.
  • 3d-inventory-schema: що несуть і зберігають. Предмети й контейнери, їх використовує 3d-unity-inventory.

Unity ніколи не є постійним власником цих даних:

Scene Schema → Unity Scene → Scene Changes → Scene Schema

Звук не має власної схеми: звукові файли — це ассети, а звуки, розміщені у світі, належать сцені.

Персонаж, камера й керування

Character View використовує 3d-unity-character для керування від першої та третьої особи. Ігри з фіксованою камерою або видом згори можуть мати власні системи руху чи команд; пакет камери не надає такого керування.

3d-unity-input → 3d-constructor-character-view-controls → 3d-unity-character
                                   ↕
                  3d-constructor-character-view-camera
  • 3d-unity-input перетворює будь-який пристрій на дії: рух, огляд, стрибок.
  • 3d-unity-character ходить, бігає, стрибає й долає схили без власної камери.
  • Керування конструктора спрямовує «вперед» за камерою, а його камера стежить за персонажем.
  • 3d-unity-xr і 3d-constructor-vr-controls роблять те саме для шолома: шолом і контролери стають тією самою CharacterCommand, тож гравець у VR, гравець на телефоні та бот використовують один мотор і одну мережу.

Один проєкт, усі пристрої

Гра — це один проєкт Unity для Windows, Android, iOS і Meta Quest. Відмінності між пристроями живуть у 3d-unity-input (клавіатура й миша, геймпад, дотик, XR) та в керуванні конструктора; відмінності між платформами — це налаштування й невеликі блоки #if.

XR вимкнено в кожній збірці, крім збірки для Quest. Код гри ніколи не торкається XR SDK: він питає XRStatus.IsActive і читає пози через EngineInput.

Мультиплеєр

Десять поточних Unity-ігор використовують 3d-unity-net, а не 3d-unity-network. Оберіть одну мережеву модель для гри: їхні API та формати повідомлень відрізняються.

3d-unity-network працює за принципом «сервер головний»: клієнти надсилають ввід, сервер вирішує влучання, здоровʼя та рахунок. Два види трафіку розділені:

  • Стан щотіку (позиції, ввід): невеликі бінарні дані всередині мережевого бекенду.
  • Повідомлення сесії (приєднання, зміни стану, ігрові події, результати): JSON у 3d-network-schema, який читають сервери, глядачі й статистика без Unity.

3d-unity-firebase зберігає акаунти й статистику між матчами, а 3d-unity-network проводить сам матч.

3d-unity-net — легший варіант: сесія з авторитетним хостом, списком гравців, іменованими подіями, позами гравців і сутностями, які публікує хост, для ігор, що будують сцени в коді й не мають префабів для створення. 3d-unity-network — повний серверно-авторитетний шар над нею.

Набір для гри

Випущена гра повторює одну й ту саму роботу навколо своїх правил. Набір для гри збирає її в одному місці, тож кожна гра пише лише те, що її відрізняє:

  • 3d-unity-shell: екрани, спільні для всіх ігор Темнороду (заставка, стартовий екран, вхід, знайомство, лобі, верхня й нижня панелі) у структурі застосунку Lords. Гра описує себе в ShellConfig і додає власні місця.
  • 3d-unity-account: обліковий запис гравця в Lords: вхід гостем або через Google за допомогою REST API Firebase, який запамʼятовується між запусками. Бути невходженим — нормальний стан.
  • 3d-unity-update: тримає гру на найновішому релізі GitHub і тихо встановлює його на Windows. Відсутність мережі ніколи не є помилкою.
  • 3d-unity-net: невелика сесія з авторитетним хостом поверх Netcode for GameObjects для ігор, що будують сцени в коді: створити гру або приєднатися за адресою чи онлайн-кодом.
  • 3d-unity-save: версіоновані локальні файли збереження, які записуються безпечно, із резервною копією попереднього збереження.
  • 3d-unity-ui: екрани, створені в коді простим uGUI, розташовані за якорями.
  • 3d-unity-synth: звуки, створені в коді з хвиль і шуму, тож аудіофайли не потрібні.
  • 3d-unity-graybox: стабільні id ассетів на примітивах і помічники Editor, що будують перший прототип.

Оболонка залежить від 3d-unity-account, 3d-unity-update, 3d-unity-net і 3d-unity-ui; решта працюють окремо.

Залежності пакетів

Граф каталогу містить залежності збірок рушія та JSON-контракти, які використовує пакет. JSON-схеми не є пакетами Unity та не входять до згенерованих маніфестів встановлення.

Принципи

  • Спершу спільне: якщо це може знадобитися кільком конструкторам, воно належить до пакета 3d-unity-*.
  • Код, потрібний двом іграм, живе в пакеті, а не в жодній із ігор: набір для гри існує, бо кожна гра мала власну копію.
  • Залежності спрямовані в один бік — вниз по шарах.
  • Ввід лише через 3d-unity-input; жоден пакет не читає пристрої напряму.
  • Жодних правил гри в пакетах рушія чи конструкторів.
  • Схеми — джерело правди; моделі рушія відтворюють їх поле в поле.
  • Необов’язкові SDK (Meta MRUK) ніколи не блокують компіляцію; Firebase не потребує SDK, він використовує REST.
